**审计视角**：**场景走通性 + 功能真实性** —— 需求定的场景在原型里能不能走完、是真逻辑还是摆设

| 场景 | 结论 | 关键断点 |

**但有 4 个会在评审现场当场穿帮的断点**，见第四节。

## 二、真逻辑：原型确实做到了什么

这几处是"真实现"，演示可以放心讲：

### 1. DCC 导入的校验链是真的（`js/components/dcc-runtime.js`）

```js
// :279  逐行必填校验，不是走形式
let reason = !leadCode ? '缺少必填线索编码'
           : !phone ? '缺少手机号'
           : !Number.isFinite(priority) ? '请填写有效优先级' : '';

// :291  同手机号独立批次 —— 需求要求的"按手机号拆批"确实成立
batchId = 'DEMO-BATCH-' + sequence;

// :331  一次请求一种业务类型，行内不一致直接冲突
// :324  requestId 幂等
```

六项来源资料**原值保存不加工**：`customer-business.js:187` 的 `importSnapshot` 只收 `typeof === 'string'`，非字符串直接判失败（`dcc-runtime.js:280`）。留资时间与平台导入时间**分开存**（`:297` 同时写 `originalImportedAt` 与 `leadCreatedAt`）—— 需求特别强调的这条做对了。

### 2. 未接通状态必选是真的，且**真的不自动代选**（`js/pages/agent-workbench.js`）

```js
// :636-638  强校验分支
const needsCallStatus = CustomerFollowup.isUnansweredOutbound(call);
const selectedStatus  = normalizeAgentCallStatus(agentCallStatusDraft);
if (needsCallStatus && !selectedStatus) return fail('请选择本次通话状态', 'seat-agent-call-status');
```

- 字典是真的：`alicti-number-status.js:4-10` 共 **20 行 / 16 个编码**，715 三条、183 三条（嘟嘟/静音/未知）
- 适用边界正确：`customer-followup.js:11-14` 限定"已结束 + 呼出 + `answered === false`"，已接通/呼入不套用
- **不代选**：`agentCallStatusDraft` 初始化为 `null`（`:598`），`updateRecordRequirements` 只回写空值（`:700-710`），演示结果分支（`:115-118`）只写号码识别，绝不写状态

### 3. 手工导入的 CSV 解析和检查是真的（`js/pages/customer-tasks.js`）

`parse()`（:126-131）是完整的字符状态机，处理引号包裹、`""` 转义、自动识别 `\t`/`,` 分隔、引号未闭合直接抛错。`prepare()`（:183）逐行校验号码正则 `/^(1[3-9]\d{9}|0\d{9,11})$/`、列数不符、备注超长、业务编码必填、同批同号重复；错误行进"未通过的行"表，且 **`确认导入` 按钮 `disabled = !preview.good.length`（:186）** —— 真的拦得住。

### 4. 报表主体是真计算，不是写死数字（`js/components/report-data.js`）

`getModel()`（:226-318）从 `CloudCallData.calls` + 批次快照 + tasks/agents/skills **实时聚合**；`stats()` 逐条算接通/未通/时长均值/首呼重呼。筛选会真的改变结果（`within()` :160 时间窗过滤），图表按 `count/max*100%` 动态渲染且可点击下钻。

### 5. 应用接入的回调地址硬拦截是真的

```js
// dcc-runtime.js:328
if (!validCallbackUrl(sourceApplication?.callbackUrl))
  return failure('CALLBACK_NOT_CONFIGURED', '请先为该接入应用配置有效回调地址，再导入客户。');
```

这是需求明确要求的"未配置回调地址不得导入"，原型做成真分支了。应用↔租户多对多也成立（`:57` `authorizedTenantIds` 为数组）。

### 6. 秒挂判定是真的（三态）

```js
// dcc-runtime.js:547
short = answered === true && hangupParty === 'customer' && trusted && duration <= 2;
// :548  三态：confirmed / not_short / pending_review —— 缺数据不填 0
```

## 三、假数据：只有一处，但很致命

全项目**只有一处**是明确的假数据，而它恰好在一个容易被演示的报表上：

**`mock/report-summaries.js` 文件抬头自述：**

```js
/* DEMO ONLY. Fixed official-shaped responses for the shipped showcase tasks.
 * No supplier calls, no statistics fabricated for user-created tasks. */
```

采样逻辑（:10-12）只认 `taskId.startsWith('SHOWCASE-')` 的内置任务，**用户自己创建的任务返回 `unavailable`**。

**后果**：外呼任务报表的「累计号码 / 累计呼叫 / 累计重呼」三列，只有在预置的 SHOWCASE 任务上才有数。演示时如果现场新建一个任务再去看这三列，会看到"unavailable"或空白。

其余 6 个报表（通话总览、线索成效、客户跟进、坐席成效、呼入服务、服务技能）走真实聚合，**不受此限制**。

## 四、四个会当场穿帮的断点（演示前必看）

### 断点 1 · DCC 导入的数据，在「客户档案」里查不到

两套存储完全不通：

```
js/components/customer-directory.js:4    → 'customer-directory-v1' / 'customer-task-batches-v1'
js/components/dcc-runtime.js:124        → 'dcc-task-ledger-v1.1.0'
```

客户档案页只读前者，DCC 账本是独立的 key。**演示时如果讲"导入后可在客户档案查看"，会当场找不到。** DCC 导入的数据只能在任务记录页里看。

另外 `dcc-runtime.js:283` 拒绝"同一手机号关联不同线索"（`'同一手机号关联多个线索尚未确认'`），与"同号可多次成批"的口径存在冲突。

### 断点 2 · 定时开始的任务，**永远不会真的启动**

`cloud-task-workspace.js` 里 `scheduleAt` / `autoStart` 只被存下来和显示（:443、:906、:935、:1458），**全文件没有任何调度器或定时器**去触发启动。选了"定时执行"、设了时间，到点不会有任何事发生。

**演示不要设定时开始，一律用手动启动。**

### 断点 3 · 新建预外呼任务时，向导里已经不能选客户名单

DCC 改造把预外呼向导第 2 步变成了"接口/手工来源"选择（:754-760），`validateStep()` :1319 在没有来源时直接报错。**与需求描述的"向导内选名单"流程不符** —— 如果按旧流程讲"第 2 步选客户名单"，界面上找不到。

### 断点 4 · 秒挂"不触发重呼"只是间接成立，2 次补提交额度压根没有

- 秒挂禁重呼：重呼条件只能选号码状态编码（`alicti-retry.js:21-22`），编码表全是未接通类（710-724、183），秒挂天然选不中 —— 但**全库没有任何 `shortHangup → 禁止重呼` 的显式代码**。问"系统怎么保证秒挂不重呼"，答不上来。
- 需求要求的"自动与人工共享首次之外最多 2 次补提交额度"**完全缺失**：`deliveryAttempt`（:361）无上限，`retryDelivery`（:511-519）可无限补送，没有任何额度计数。

## 六、演示建议

**能放心演示的**
- 应用接入配置回调地址 → 未配置时导入被硬拦截（`CALLBACK_NOT_CONFIGURED`）—— 这条最有说服力
- 坐席拨号 → 振铃期填单 → 未接通时状态必选 → 保存后继续跟进 → 在待联络列表再找到
- 手工导入：传一个故意做错的 CSV，让"检查名单"报错、确认按钮置灰
- 6 个真实聚合的报表（避开"外呼任务"）

**必须避开的**
- 不要在 DCC 导入后去「客户档案」找数据（找不到）
- 不要设"定时开始"（不会启动）
- 不要用现场新建的任务看外呼任务报表的累计三列（unavailable）
- 不要讲"11 类失败原因"（只有 3 条样例）
- 不要演示完坐席填单后关闭标签页（草稿丢失）
- 不要问"秒挂为什么不重呼"（没有显式规则）

**需要提前补的（若要对外正式评审）**
1. 打通 DCC 账本与"客户档案"（或明确说明 DCC 数据只在任务记录页看）
2. 补 11 类失败原因字典
3. 补"首次之外最多 2 次"的补提交额度计数
4. 补秒挂禁重呼的显式规则
5. 定时开始：要么加调度器，要么在 UI 上明确标注"演示不实际启动"
6. 报表：为自建任务提供聚合兜底，或明确标注"仅内置任务有供应商累计数据"

## 附：审计方法

- 场景清单取自 `需求/1.1.0/今日确认基线.md`（本轮 12 故事 / 104 验收 / 7 场景）
- 原型能力地图取自 `js/nav.js` 菜单定义 + `window.Pages` 全部注册点（20 个页面）
- 每个场景：定位入口 → 读实现 → 判断"真逻辑 / 假数据"→ 记录缺口
- **"真逻辑"判定标准**：有状态机、数据真落盘（localStorage）、有校验分支、操作后数据真的变了
- **"假数据"判定标准**：数字写死、切换筛选结果不变、点击只是切 tab、图表为静态占位
- 所有结论均经二次核对，文件:行号证据已抽查验证（含 `mock/report-summaries.js` 自述、定时开始无调度器、两套存储 key 隔离）
