# v1.1.0 本轮审阅：接口导入业务类型

**12故事／104验收／7场景，S1／S2定点检查22／16通过。** 本文件沿用既有审阅入口；本次局部修改、开发包同步及GitLab推送已获用户授权，正式G1／G2／G3未批准，生产接口与完整版本仍待核。

## 本次产品结果

业务系统通过 API-001／DCC-RST-IMPORT 在请求层必填 `businessType`。一请求一种类型，必须是当前已验真token租户下启用的稳定业务类型编码，名称只作展示。不同类型分次导入仍可共用businessBatchNo。缺失、无效、非当前租户或停用类型的新业务拒收，不保存客户、不分配、不提交供应商；不由source、callMode、号码或任务默认值猜类型。

逐条保存原编码和名称快照；客户名单、客户详情、准确本次通话详情显示原类型；拨号／振铃早填按原类型载入表单，接口线索不重复选择或静默换类型。改名／停用不重写历史，原表单不可用说明原因并保留草稿；历史缺值显示未提供，不能默认其他表单。

每次结果／进度以及“本次通话结束＋已完成沟通＋保存成功”的快照回调都带原businessType稳定编码，与原app/tenant/record/call和原业务批次关联。已有六项来源字段、线索编码及已填业务字段／选项业务编码继续。补送沿原事件快照，不读最近同号或新配置替换类型。

## 校验、重放与兼容

- 当前身份和租户／应用资格先验真；完整幂等内容包含businessType。同app+tenant+requestId同内容技术重放取原受理回执，不重复导入，也不因后来类型停用改写已受理请求；同ID改类型冲突。
- 类型不进入原线索／批次归组键或失败额度键，不因另开类型重置额外2次；不替代来源、外呼方式、taskId、坐席工号或leadCode。
- 原手工流程已有业务类型，继续保留其选择、单一线索编码、原弹窗和选填后置；无新增页面或类型管理功能。API-002仍是AliCti供应商接口，不加未经证实的businessType。
- 正式类型码集合、字典来源／版本、字段长度／旧客户端迁移、原表单配置版本及真实持久和回调继续归ISSUE-044／045／046等既有缺口；本地模拟不证明生产实现。

## 已确认的业务要求

| 项目 | 当前要求 |
|---|---|
| 租户与应用 | 多对多：一个应用可关联多个租户，同一租户可关联多个应用；各应用分别配置回调地址 |
| 接口导入方式 | 指定预外呼或人工外呼；人工外呼指定坐席工号，预外呼按任务坐席组分配 |
| 应用回调 | 应用保存回调地址，所有接入业务系统都需要回调，包括天网 |
| 导入前校验 | 未配置回调地址，不允许通过接口导入；提示先补配置，不先收后积压 |
| 振铃时填写 | 坐席工作台振铃期间即可填写客户跟进表单 |
| 未接通保存 | 原跟进表单增加通话状态选择，采用AliCti号码状态712等完整枚举；适用条件及保存边界见下文 |
| 继续跟进 | 处理结果选“继续跟进”后，线索继续保留在待联系列表 |

“人工外呼”是呼叫方式，“手工界面导入”是线索来源。来自应用接口的人工外呼同样需要回调；手工界面导入没有外部业务接收方，仍在平台查看。此前“天网只查看、只有 DCC 回传”的范围已被本次明确替代。

## 坐席操作方案

1. 振铃时直接显示原有跟进表单，保留接听、取消或挂断等适用通话操作；状态切换时已填写内容保留。
2. 明确本次外呼客户未接且通话已结束时，在原表单必选“通话状态”后保存，“处理结果”单独填写。选择项采用API-327完整20项描述、16个编码，包含712拒接；715/183同码多描述按编码与描述成对保存。明确选择183“未知”有效，空白未选不可保存；客观未知不自动代选。客户已接通、客户接通情况未知，以及预外呼客户已接而坐席未接，不套客户未接必选规则；呼入不扩展。其他业务字段条件必填、正式存储和接口契约仍待核，不强迫填写或编造必须经沟通才能获得的信息。
3. 选择“继续跟进”并保存成功，当前已归属坐席的人工线索留在其待联系列表，已有跟进内容可查，再次联系沿原入口进行；不因保存本次记录就把线索标成已完成。
4. 保存失败时保留表单内容和待联系记录，明确提示重试；重复保存不产生重复跟进或待联系条目。

第1～4项包含用户要求及本方操作细化；本次仅确认通话状态选择与字典并登记适用边界。其余草稿恢复、保存事务和各业务字段条件仍待审，不能据此宣称完整工作台或生产接口已经验证。沿用现有界面结构；“继续跟进”应兼容旧内部值“需要再次联系”，避免改显示名称后误标完成。

坐席填写的通话状态与线路实际结果分别保存。人工外呼的客户振铃，与预外呼的坐席振铃不同；预外呼客户可能已经接通，不能因为坐席未接就改记客户未接。已填写内容不应因坐席未接的自动关窗而丢失。人工填写不改接通统计或秒挂判定；呼入业务没有在本次外呼增量中另行扩展。

## 租户身份与继续跟进归属

用户已纠正原一对一和共享唯一应用方案，现为多对多、各应用独立回调。身份建议如下（正式字段与工程协议待S3／S4核验）：

1. 业务系统用自己的应用凭据，获取token时明确传入租户编号。
2. 平台校验该应用与所选租户的有效关联，签发绑定应用和该租户的token。缺少租户编号不自动选第一或最近租户。
3. 导入按token租户处理。报文租户、预外呼任务或人工坐席工号不属于该租户时拒绝，不用一枚token临时切换租户。
4. 原始记录保存应用和租户归属，结果发往该应用配置的回调地址，报文保留原租户和记录标识供业务方区分；来源声明只做一致性校验，不能更换发送目标。不同应用／租户的请求去重、结果和权限互相隔离。

预外呼接入坐席后选择“继续跟进”，已确认由当前坐席后续人工跟进，线索进入其待联系列表。原预测任务、原记录、来源和通话历史需保留。设计必须避免与原任务自动呼叫并行；供应商停止后续重呼的真实能力及成功判据仍待核验，不能把本地转入名单当作远端已停止的证据。

### 共享导入与DCC确认的关键约定

- 请求作用域建议为可信租户＋稳定app＋操作＋requestId，taskId与完整业务输入进入比较；同app换有效token仍在原域，不同app同requestId隔离。当前认证和任务权限先于重放查询。
- 按稳定且版本受控的归一规则比较tenant/task及全部请求行的完整业务输入，包含校验失败/待核行，不先丢弃错误行再只比较成功/有效行。行数、行定位及全部业务字段须参与比较；missing isNewBatch与显式false归一相同。坏行业务输入变化、行增删/重排与空白/数字编码/可选R等差异如何规范化须由工程明确并固定，不随每次实现忽略；归一完整内容不同即整重复请求冲突。
- 同ID同内容返回原所有逐行接收回执及record/batch/root，不因后来新主重选root或重新导入；同ID异完整内容整请求冲突。新请求才按既定逐行规则建立业务记录。

**A的实现依据与适用边界。** [WHATWG文件系统规范](https://fs.spec.whatwg.org/#api-filesystemwritablefilestream)提供可等待的写入流关闭结果；[Chrome官方文档](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)给出相应保存路径与能力检测。候选在完整内容校验后等待`close()`成功，再读取同一文件核对字节数和摘要。[文件选择器规范](https://wicg.github.io/file-system-access/#api-showsavefilepicker)要求安全上下文、用户操作触发及相应授权，所选位置也可能由云盘提供。因此，实际支持表、正式HTTPS部署、嵌入方式及终端策略仍待工程验证；只见到API名称不算可行性通过。

完成回执属于受认证客户端对这次保存的报告，能用于正常受控页面中的工程判定；**它不是服务端可独立验证的操作系统落盘证明**。快照身份、一次性凭证和摘要可以防止混淆或重放，不能证明被篡改客户端确实执行了保存。该方案也不证明用户已阅读、永久保留、云盘同步完成或断电后仍可恢复。工程须先明确所需信任等级；若要求防客户端伪造的独立证明，应另评受管扩展／客户端及其部署成本，不能凭空把A升级为该能力。

普通网页不能直接使用[HTML规范中的WebDriver BiDi下载完成事件](https://html.spec.whatwg.org/multipage/links.html#downloading-resources)；这是自动化协议钩子。[Chrome下载监测接口](https://developer.chrome.com/docs/extensions/reference/api/downloads)则要求扩展安装与权限，也不能作为网页现成能力。浏览器内部存储中的文件副本同样不能冒充用户取得导出文件。
