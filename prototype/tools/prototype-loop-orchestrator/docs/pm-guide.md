# PM 使用指南

本文面向产品经理，说明如何发起、确认和评审一个原型 loop。本文不定义执行门禁，执行以 `orchestrator/` 和项目内 `tools/loop_run.py` 为准。

## 发起方式

当需要把需求生成可评审原型时，输入“开始计划项目”，并尽量提供：

- 产品目标
- 目标用户
- 页面范围
- 非本期范围
- 核心流程
- 关键数据对象
- 参考项目、截图、FLOWCHART 流程图、API 文档或历史项目
- 迭代方式：新建项目或基于现有项目迭代
- 是否明确需要功能说明文档（默认不生成）
- 是否明确需要页面标注提示词与覆盖清单（默认不生成）
- 验收标准
- 交付方式

如果只输入“开始计划项目”，Agent 必须先追问这些内容，不能直接进入项目拆分或实现。

如果本轮有新的业务需求，推荐先让需求分析 Loop 完成用户故事、场景泳道图、交互时序、接口核验、产品与流程基线、功能清单和页面规划，并在 G3 由 PM 冻结。原型 Loop 接收该 ZIP 后不再重复追问业务事实，只确认演示目标、受众、视觉、设备、底座、交付方式，以及是否明确需要说明文档或标注。

## 必须确认的内容

进入实现前，必须确认：

- 产品目标
- 目标用户
- 范围和非范围
- 输入材料
- 迭代方式
- 功能说明文档：生成或不生成（默认不生成）
- 页面标注：生成手动提示词与覆盖清单，或不生成（默认不生成）
- 核心页面
- 核心流程
- 主要数据对象
- 验收标准
- 交付目标

确认结果必须先写入项目启动规划。PM 明确确认后，总控在 S2 记录本轮名称、确认人、当前会话确认依据和两个可选交付开关，并把启动规划和 CLAUDE.md 的内容摘要绑定到审批记录；导入需求分析包时还会绑定其 manifest SHA-256。没有明确要求时两个开关保持 false。文件或冻结包之后发生变化会要求重新确认。

S2 确认后，Agent 需要写入项目级 `CLAUDE.md`；S3 再把启动规划或冻结基线转换为 `memory/project.md`、`memory/business-rules.md`、`memory/feature-list.md`、`memory/source-materials.md`、`memory/field-map.md` 和 `memory/open-items.md`。这些机器状态和记忆文件由脚本和 Agent 维护，PM 不需要手动编辑。

## 评审产物

交付时应能看到：

- 可打开的静态原型
- 业务流程图
- 时序交互图
- 关联系统展示（可选内容）
- 已知限制
- 验证摘要
- 功能说明文档（仅明确要求时）
- 页面标注提示词与覆盖清单（仅明确要求时）

生成项目顶部固定提供四个核心交付视图，并按需增加说明文档：

- 原型页面：进入业务原型和业务导航。
- 业务流程图：展示角色泳道、业务节点、判断条件和回流路径。
- 时序交互图：展示用户、页面和系统之间按时间顺序发生的请求、响应与状态变化。
- 关联系统展示：展示外部平台和上下游关系；当前项目没有关联系统时允许为空。
- 说明文档（可选）：只有明确要求时展示交互、状态、数据来源、验收规则和已知限制。

这些入口独立于业务侧栏，并在当前页面内通过统一内容区切换，不发生整页跳转；URL 的 `#delivery=` 会保留当前选中视图。未请求说明文档时不显示对应入口。

明确请求说明文档后，入口直接加载 docs/interaction.html，不再额外维护一个重复的 docs/index.html 中间页。

说明文档统一采用“功能说明文档”格式：版本说明、项目范围、逻辑说明、功能说明、其他说明五章。功能说明按页面或完整业务功能拆分，每节包含功能名称、交互说明、数据来源、逻辑说明和七列功能明细表。文档使用白底表格型版式和蓝色标题/按钮，不生成 Hero、卡片看板或营销式概览页。

## 维护流程与关联系统页

生成项目固定包含 `flowcharts/business-process.html`、`flowcharts/sequence-interaction.html` 和 `related-systems/index.html`。S6 会把前两张图拆成实现步骤。普通模式由 S7 根据项目记忆生成 HTML；导入需求分析基线时，S7 直接复用其中已核验的 HTML 图集，只增加原型导航和来源标识，不重新布局泳道或连线。S8 与 final 对图类型、节点、关系、基线指纹和本地导航进行检查。

业务流程图和时序交互图是必选交付，不接受外部链接、远程 iframe 或流程截图代替。关联系统页面壳始终存在；只有项目记忆明确记录了外部平台、上下游或依赖系统时才生成内容，否则显示明确空态。

旧项目缺少统一交付视图时，由 Agent 在 loop 源仓库执行 `create_project.py 目标项目路径 --sync-delivery-pages`。该操作会补齐四个核心视图的切换壳和缺失内容页，不主动创建说明文档；已有说明文档正文会保留，并由工作流开关决定是否显示入口。

继续修改已有原型项目前，总控会先从当前安装技能执行 `create_project.py 目标项目路径 --sync-runtime`。它只刷新项目内 loop 脚本、阶段技能、可选视图导航和共用样式，保留业务页面、项目记忆、标注、已有说明文档正文和已经生成的本地 HTML 图内容。

## 查看当前状态

产品经理不需要理解脚本细节。每次运行 loop 后，可以查看：

- `memory/loop-status.md`

该文件会用人话说明：

- 当前阶段是什么
- 是否可以继续
- 阻塞原因
- 需要 PM 确认什么
- 需要 Agent 补齐什么
- 下一步建议

内部执行文件如 `execution-steps.md`、`acceptance-map.md`、`workflow.json` 主要服务于系统追踪，不应成为 PM 的主要操作界面。

项目完成后若继续下一轮，总控使用 begin-iteration 先归档上一轮状态并回到 S0。若终态后新增说明文档或标注需求，总控使用 request-deliverables 记录明确请求并回到 S9；已请求标注且 PM 手工回写后，再使用 approve-annotations 重新验证。

## 交付（loop 外手工）

loop 在 S9 收尾终检通过后结束。把原型推送到 GitHub 是 **loop 外的手工步骤**——loop 不自动建仓或推送。本地 `git` 初始化、提交后推到预先创建的远端仓库即可。

## 边界

本 loop 生成演示原型，不承诺直接生成生产系统。真实后端、数据库、认证、安全合规、部署和生产级 QA 应作为后续工程化事项记录。
