**三、实施时必须保留的产品关系**

- 字段归属品牌，导入字段与填写字段分别保存、分别引用，同名不合并；导入字段业务编码必填并用于业务映射，不新增格式配置。
- 模板的“字段参考分类”只提供编排字段。实际业务分类独立绑定执行路由，不能因模板参考了某分类就自动建立运行关联。
- 导入支持 `DIRECT` 直接跟进和 `TEMPLATE` 按模板流转。分类控制是否允许直接跟进；两种模式均遵守导入字段校验。直接跟进不要求满足模板路由条件，按模板流转须满足其准入规则。
- 导入及分配明确外呼方式，AI 外呼须使用合法的本租户 AI 场景；分配负责安排跟进人。跨租户承接按转交规则办理，由目标租户分配和呼叫，不能只切换呼叫资源而跳过业务归属处理。
- 模板采用开始、转交、呼叫、结束四节点。导入条件可独立判断；通话及标签条件使用对应执行来源的准确事实。运行创建时固定完整方案，分类换绑影响后续新运行；已创建运行按原方案完成或受控废弃。
- 当前有效值与每轮跟进快照分别保存。新一轮按规则取得最新数据，谁实际接听处理谁填写；已形成的内容和通话事实快照保留原貌。字段、选项、业务、运行、跟进、执行段和通话使用稳定身份关联。
- 受理、真实拨打、通话结束、填写保存、归档、人工确认推进分别记录；未知结果先核对原请求。END 按配置关闭业务或转入无模板人工跟进周期，不自动起呼。
- 保留原 AI、Cloud、IVR、资源、服务、录音、报表和审计能力，沿原权限和数据范围承接。此次不新增旧规划的历史兼容或迁移工作，原专业来源契约仍须核证。

完整行为、异常和字段规则以当前交接包为准；本说明不替代任务卡与验收正文。

**四、实施顺序**

先完成第 1 步的工程准备与开工核验，再进入正式业务实现。下表用于安排工作主线；每项任务仍须满足任务卡的 `depends_on`。仅任务依赖通过尚不足以判断并行安全，共享物理文件的写入顺序须在工程绑定后补齐。

| 顺序 | 实施内容与任务 | 交付重点 |
| --- | --- | --- |
| 1 | 工程准备和契约验证 | 指定目标库、七类工程决定、12 组真实契约责任，完成模块/字段/接口/文件/验证映射；按当前门禁完成实际评审与版本确认。准备阶段可先做脚手架和技术验证。 |
| 2 | 身份、租户与权限：TASK-001～007；供应商接入：TASK-055 | 统一身份、品牌/租户关系、模块独立授权、撤权和引用保护；先确定真实供应商及执行资源归属。 |
| 3 | 字段与配置：TASK-008～013；依赖满足后推进专业底座 | 完成品牌字段、分类双 Tab、参考模板、实际路由与列映射。同时按依赖推进 TASK-032/033 场景标签、TASK-037～039 联系限制、TASK-049～056 坐席及资源等专业支线。 |
| 4 | 导入、分配与执行资格：TASK-014～016、029、031 | 整批预检、正式导入、业务身份及批次、责任人安排、未知请求核对、同号占用。TASK-016 依赖 TASK-032/049，专业底座须先就绪。 |
| 5 | 呼叫与跟进归档：TASK-018～021，再推进 TASK-017/022 | 单条及合法同组批量起呼 → 准确回执/标签 → 本人填写与取数 → 唯一归档；随后完成直接跟进的结束/再次跟进和有效资料更正。TASK-018 还依赖 TASK-039/042。 |
| 6 | 模板流转与业务闭环：TASK-023～028、030 | 条件计算、确认推进、END 接续、跨租户转交、废弃/重新办理、分类调整、直接业务启用模板、统一队列及时间线；按各任务依赖实施。 |
| 7 | 补齐并回归全部专业能力：TASK-032～056 | 专业支线随依赖提前实施；本阶段核齐 222 项既有能力、十类报表、录音、服务与审计。TASK-047 报表依赖跟进归档及相关专业结果，安排在事实链具备后。 |
| 8 | 跨任务验收与真实联调 | 执行下述六批验收，留存环境、请求、回执和实际结果；实现或来源变化后重验受影响项并完成联合复核。 |

尤其不能把所有专业模块放到业务链末尾才开发：人工起呼依赖电话与联系限制，分配及 AI 安排依赖场景和坐席，完整依赖见 [任务计划](https://github.com/hw00913-bot/callcenter/blob/2.0.0/2.0.0/开发交付包/当前交接包/task-plan.md)。

**六、真实接口联调与补证事项**

以下 12 组均为当前开放工程问题。开发需逐组指派负责人，提交真实契约版本、字段映射、测试环境及请求/响应或事件证据。Mock 结果只承接产品预期，真实成功、失败、未知、重复、迟到与重试结果由联调确认。

| 问题编号 | 需要补齐和验证的事项 |
| --- | --- |
| ENG-FLOW-PERSISTENCE | 业务、运行、跟进、执行段、通话、请求的生产模型与关联；正式入站导入、稳定业务编码、列映射、原始值、重复幂等；同次写入的事务、唯一性和并发控制。 |
| ENG-FLOW-EXECUTION | AI/人工/预外呼的请求 ID、任务 ID、供应商 callId 和事件身份；受理/拨打/通话终态/重试收敛/内容保存准确关联；重复、乱序及迟到事件的处理。 |
| ENG-FLOW-SCENE | 由哪个服务提供供应商、租户、类型、标签场景、分类、品牌和修订信息的最小只读投影；准确验证当前租户可用 AI 场景。 |
| ENG-FLOW-CHECKS | 把产品 CHECK 接到真实 CTI、回调、文件、同号并发和幂等测试环境及 CI；保留原验收 ID 与预期。 |
| EQ-PLAT-IDENTITY | 真实认证主体、统一账号/租户与 AI 租户/Cloud 企业的权威映射、模块及功能授权、资源使用权、会话退出和撤权生效；验证 AI-only 等独立模块授权组合。 |
| EQ-PLAT-CONTACT-STATE | 当前生产限制记录的 sourceId、来源、有效期、解除码和状态；同号多来源聚合及读取一致性，解除/到期后旧事件不得恢复限制。 |
| EQ-PLAT-ACCEPTED-CALL | 逐供应商核实“已受理但未拨”号码能否阻止、取消或删除，操作时点与队列一致性；不支持的能力形成明确差异结论。R-154 的真实能力仍待开发验证。 |

**七、验收顺序与接包回传**

当前原型已记录 38 组、523 项本地用例通过，五角色 91 次页面检查覆盖 43 页；有限 Mock 的 S8/final 通过且快照干净。真实认证、CTI、供应商、账务和生产部署由开发补验，`file://` 自动化未在本轮验证。完整范围见上方验收报告。

工程实现按 [原跨任务验收批次](https://github.com/hw00913-bot/callcenter/blob/2.0.0/2.0.0/开发交付包/当前交接包/接包执行顺序.md) 执行，批次复用原 CHECK，存在跨批次重叠：

2. **BATCH-02**：字段、分类、参考模板、实际路由及两种模式导入。
3. **BATCH-03**：DIRECT 人工/AI/预外呼完整周期及显式启用模板。
4. **BATCH-04**：TEMPLATE 入口、条件、流转、转交、结束及再次办理。
5. **BATCH-05**：原 AI/Cloud/IVR、接口、报表及服务专业能力。
6. **BATCH-06**：未知、重试、并发、迟到、同号限制和跨域可见性。
